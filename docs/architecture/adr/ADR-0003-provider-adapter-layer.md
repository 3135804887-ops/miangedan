## 背景

面个蛋依赖五类外部能力：LLM、ASR、TTS、数字人、搜索。PRD 要求：

- 每项核心能力至少验证一个主方案和一个替代方案（Phase 0 出口）；
- 按地区、语言、延迟、质量和可用性路由；供应商紧急停用时切换已验证替代（US-08 场景 5）；
- 中国区内容不默认调用境外模型；密钥由独立密钥系统管理；
- 不在 PRD 中锁定单一商业厂商（OD-01 未关闭）。

若业务代码直连厂商 SDK，则切换供应商等于重写链路，故障切换与区域合规都无法保证。

## 决策

建立统一**供应商适配层**（模型网关的一部分）：

1. 为五类能力各定义一份供应商中立的能力接口（能力发现、健康检查、延迟与质量指标、故障语义），契约见 `docs/ai/PROVIDER-ADAPTERS.md`。
2. 业务代码只依赖能力接口；厂商差异封装在各适配器内。
3. 路由按数据区、语言、能力与实时健康决策；熔断、切换、灰度在适配层执行并写审计。
4. 活跃正式面试固定开始时的供应商与模型版本；切换仅在故障恢复路径内发生且必须记录原因。
5. 供应商凭证按数据区隔离注入（`.env.example` 的 `[REGION-SCOPED]` 组），适配层是唯一直面凭证的组件。

## 理由

- 可替换性直接是 PRD 发布门槛（核心能力必须有已验证替代方案）。
- 区域合规（cn/eu/intl 各自的供应商白名单）需要单一执行点。
- 版本固定与灰度（离线→影子→灰度→放量）需要统一注册表与路由控制。

## 替代方案与拒绝原因

1. **业务代码直连厂商 SDK**：切换成本高、区域合规无法统一执行、密钥散布。拒绝。
2. **只抽象 LLM，其余直连**：ASR/TTS/数字人同样存在 P0 故障风险与区域合规要求。拒绝。
3. **引入第三方网关产品代替自建适配层**：能力语义（回合检测、打断、口型、区域路由）高度产品化，通用网关无法表达；可在其之上封装但不替代适配层。拒绝。

## 影响

- 正面：主/备切换、灰度、区域合规、密钥隔离单点执行；Phase 0 对比评测有统一度量口径。
- 代价：需要为每类能力维护接口契约与适配器测试；接口要克制抽象，避免最低公分母损失能力（如打断、口型同步必须是一等语义）。
- 后续动作：制定五份能力接口契约（TASK-030）；供应商注册表与灰度守门（TASK-080/081）。

## 验证方式

- 契约测试：每个适配器跑同一套能力一致性测试套件。
- 故障演练：主供应商断连 10 分钟内完成切换且活跃会话按冻结/恢复规则处理。
- 静态检查：业务代码依赖白名单（禁止直接 import 厂商 SDK）。
